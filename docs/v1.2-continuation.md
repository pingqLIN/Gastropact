# Resume and complete a v1.2 task

Gastropact keeps the sealed task definition separate from progress and result evidence. This guide applies to an existing, authored and sealed `task-contract.v1.2` bundle. The templates need project-specific values and authorization before use; they are not ready-to-run tasks.

## 1. Inspect the saved task

Begin each handoff with read-only intake, replacing the placeholders with your approved paths:

```shell
python scripts/task_contract.py resume --task <task-dir> --project <project-root>
```

Continue only after `RESUME_OK`. Check the task ID, schema version, revision and next action in the output. `resume_mode=READ_ONLY_INTAKE` reports saved state; it does not authorize execution. Obtain the action's required current authorization and satisfy its hard gates before dispatch.

If intake returns `STOP`, preserve the bundle and resolve the reported mismatch. Do not reconstruct authority from conversation history or bypass a stale seal, revision conflict or audit gap.

## 2. Save an interruption

A v1.2 checkpoint records an interruption without completing or advancing an action. Use the observed revision and current action ID, and omit `--completed-action-id`:

```shell
python scripts/task_contract.py checkpoint --task <task-dir> --project <project-root> --expected-revision <revision> --status RUNNING --current-state "Paused at the current action" --next-action-id <current-action-id> --note "Interruption snapshot"
```

Run this only when authorized to update the task. Re-read the revision after a successful checkpoint; it advances the state revision while preserving completed actions. Another writer's stale revision is rejected.

`checkpoint --status PASS`, a completion ID, or a different next action is rejected with `automation_result_required`. v1.0 and v1.1 keep their own checkpoint rules. A legacy v1.2 checkpoint event containing a non-null `completed_action_id` causes `resume` to stop with `audit_gap`; the tool does not rewrite or migrate it. Preserve such a bundle and use a reviewed recovery procedure.

## 3. Dispatch and submit bound evidence

With the required authorization in place:

```shell
python scripts/task_orchestrator.py dispatch --task <task-dir> --project <project-root> --owner <owner>
```

Use the resulting envelope to prepare an [executor result](../schema/executor-result.schema.json). Bind it to the exact task, contract hash, state revision, action, workspace baseline and lease. Evidence must use the supported verifier and match the required evidence classes, artifact digest and size. Artifacts must satisfy the action's scope and provenance rules; a pre-existing or unrelated file cannot substitute for the action's output. Verification checks must reference known evidence IDs.

```shell
python scripts/task_orchestrator.py submit-result --task <task-dir> --project <project-root> --owner <owner> --result <executor-result.json>
```

Action completion and terminal PASS use this result path. `RESULT_COMMITTED` is a local transition receipt; acceptance of the work still belongs to the task lead. A duplicate must match the existing result and transaction bindings. Reusing an ID with different content is rejected. Idempotent local submission does not guarantee that external side effects happen only once.

## 4. Verify the behavior

With the repository verification dependencies available:

```shell
python -B -m unittest tests.test_task_contract.TaskContractV12ContinuationTests -v
pwsh -File automation/verify.ps1
```

The eight continuation tests cover read-only intake, interruption snapshots, completion and advancement rejection, stale revisions, legacy events, evidence-bound terminal results and duplicate submission. The full gate also covers synthetic process-exit recovery and POSIX locking. POSIX tests are skipped on Windows.

These tests do not establish physical power-loss durability, remote executor identity, remote CI success or production acceptance. See the [README limits](../README.md#scope-and-limits).
